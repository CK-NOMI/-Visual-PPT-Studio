# DeepSeek 成本、流量与修复可靠性优化方案

日期：2026-10-15。状态：已获用户授权并实施；结果见 [API_COST_IMPLEMENTATION.md](API_COST_IMPLEMENTATION.md)。下文保留原方案及其当时的基线；未发起真实 API 测试。

## 1. 当前基线与判断

依据 `workspace/visual-agent-s001-isolated/api_usage/requests.jsonl` 的 55 条请求及对应候选文件：

| 指标 | 实测 |
| --- | ---: |
| 已记录请求 | 55 |
| Visual Agent 请求 | 51 |
| 已知输入 / 输出 Token | 5,034,699 / 35,382 |
| Visual Agent 输入 Token | 5,024,961 |
| 已知费用估计 | 约 ¥10.0747，含节假日未核实的峰时上界 |
| 图片编码载荷，含失败尝试 | 370,366,908 字节，约 370.4 MB |
| 请求内容总量，含失败尝试 | 385,621,749 字节，约 385.6 MB |
| Visual Agent 用户文字载荷 | 15,158,839 字节 |
| 最终交付验收 | 0/2，通过前有中间候选，不能解释为完全没编辑 |

这些字节是应用统计的请求内容，不能冒充运营商流量；失败请求可能未传完，HTTP 开销、网络重传和其他程序流量也不在其中。缺 usage 的请求不能当作零费用。

必须分开解决两个问题：重复上传图片消耗流量；庞大的文字上下文和过多回合消耗输入 Token。不能把图片的 Base64 字节数当作模型 Token。

当前官方 Vision 文档说明，图片按图像尺寸转换为 Token，每张存在 1024 Token 上限。当前 51 次 Visual Agent 尝试含 174 个图片块；即使所有尝试都成功，按该文档计算的图片上限也只有 178,176 Token。实际图片/文字的精确拆分仍需服务端更细 usage 或对照实验，不应凭字节比例分配账单。这进一步支持先调查文字上下文，而非先降低图像清晰度。

## 2. 最明确的文字负担

`studio/ai.py::visual_agent_turn` 将每个对象的完整 `text_layout` 放入请求。

本次两个任务对应的候选文件：

- S001：`6d4d98dcf358/build/visual_agent/cf34b3e195d14482b35b6a8bbb460ac3/candidate_project.json`，106 个对象，`text_layout` 合计约 178 KB。
- S002：`6d4d98dcf358/build/visual_agent/3115812e1a284a67868a59a04f29d3b6/candidate_project.json`，138 个对象，`text_layout` 合计约 233 KB。

以上路径相对实际工作区 `workspace/visual-agent-s001-isolated`。其中 `text_layout.font` 分别约 69 KB / 89 KB，含反复出现的字体文件路径、文件哈希、别名和文件身份信息。`text_layout` 还重复携带 text、source_text、box、OCR box、引擎版本、输入签名等。这是候选文件的结构尺寸；不能宣称它们就是某个历史 HTTP 请求的精确内容或 Token 拆分。

方案：新增专供模型阅读的对象投影；原始对象和渲染数据完整保留。投影保留对象 ID、类型、完整文字、位置尺寸、字体和实际回退字体、字号、颜色、粗细、对齐、行距字距、旋转、层级、语言/公式类型、行与 run 关联，以及当前问题相关的墨迹边界、基线、空白和溢出证据。

字体文件哈希、绝对路径、重复字段等默认不进入每轮模型输入；字体身份映射在本地保留，涉及字体替换或一致性问题时按需提供。问题区域对象提供详细证据，其他区域仍提供全页对象概览，避免失去全局上下文。

历史不再直接序列化整条渲染和工具档案。向模型提供按问题整理的状态：做过什么、实际改变了什么、最新截图对应的版本、为何失败、下一步需要解决什么。底层完整轨迹仍保存在本地；带原生 tools 的思考调用必须完整遵守 reasoning_content 协议。

## 3. 第一批：优先解决流量，保持图片内容

使用官方 Files API，将原始图片上传一次，后续以 `file_id` 引用。Design、渲染和局部图分别按文件内容哈希去重；同一图片不因文件名变化重新上传，图片内容改变则必须生成新引用。

- 保持当前图片像素、颜色和视觉证据；先不做有损压缩、不删除现有局部图、不合并图片。
- 缓存按接口地址和凭据身份隔离；不在日志中记录 Key。文件设置有限有效期，例如 24 小时，避免默认永久保留。
- 文件失效允许有界重传；接口不支持时明确显示降级和新增传输量，避免静默反复上传。
- 把上传流量、请求载荷、引用次数、去重节省量分别加入监控。引用图片仍作为视觉输入，不能因为请求中只有 file_id 就漏记图片。
- file_id 不等于免费读取图片，也不保证自动提高推理缓存命中；费用仍以返回 usage 为准。

先用 Mock 验证图片不变、去重、跨凭据隔离、过期及失败处理。真实接口兼容性留到用户确认后的少量实验。

## 4. 第二批：减少单轮文字，不改变修复决策

实施上节的对象投影与问题历史摘要。完整 Design、当前实际渲染和全页对象概览继续提供。固定任务规则和工具定义前置，当前问题、版本、对象变化和最新工具结果后置。

调试模式可以在本机比较“原对象与模型投影”的字段覆盖，但不记录完整用户文本。监控补充对象概览、问题详情、OCR、工具反馈、历史摘要的字节数，作为定位数据；正式输入 Token 仍只取 usage。

这批先不改变每次编辑后的渲染和视觉复核、不调低模型、不削弱公式识别。

## 5. 第三批：让循环以实际进展推进

当前 `studio/server.py` 有多个额外诊断分支，单问题默认最多 10 次尝试，总尝试上限可达 50；尝试次数不等于 HTTP 调用次数，因为读取、no-op、跳过后的诊断和复核还会追加模型请求。

建议按以下顺序改进：

1. 一次全页诊断建立问题清单；允许 DeepSeek 在同轮给出多个互不干扰问题的修复批次。跨同一行、同一卡片、同一公式的对象作为关联组处理，不能机械逐框修改。
2. 本地执行修改并做真实渲染，再交给 DeepSeek 复核该批问题及全页回归；仅跳过一个问题时，本地推进已有队列，避免每次重做完整诊断。仍保留阶段性和最终全页检查。
3. 同样参数返回 no_change 时，向模型提供实际文字、相邻对象、空白宽度、墨迹边界和上次结果。文字已正确但间距仍错时，应修改布局；不应再提交相同文字，也不能自动标记已修复。
4. 为问题建立包含对象组、修复目标和页面版本的稳定身份，防止换 issue ID 后被当成新问题。根据对象和相关截图是否变化判断进展，不能只按文本参数相同就拒绝所有后续修改。
5. 同一问题连续两次没有状态变化时，升级一次有明确新证据的聚焦诊断；仍无进展则保存最佳候选、明确剩余原因并暂停该问题。继续其他独立问题；最终交付状态如实保留未解决项，可从断点续修。
6. HTTP 401/402 等明确不可继续的失败立即停止本次 API 调用链并保存候选；不逐问题继续发送。网络中断如无法确认服务端是否执行，应标记用量未知并有界重试。

“暂停”是防止同一失败动作继续收费，不能变成把问题判为通过。DeepSeek 继续负责视觉判断和修复方案；程序负责如实执行、检查实际变更和管理任务状态。

## 6. 预算与成果保存

新增每任务的费用/请求数/传输量预警和可恢复暂停。阈值由用户设置，不把固定少量轮数当作所有页面的质量上限。达到预算后展示已修复项、剩余项、当前最佳候选和继续按钮；预算是用户控制开销的机制，不是质量验收条件。

费用统计可能有未知请求和在途请求，无法承诺精确到分的硬上限；预算界面应显示未知量和估计边界。

成功的中间修改必须保存并可继续。局部修复通过、整页交付通过、是否写入正式项目分别展示，避免“还剩一个问题”让用户看起来所有修复都消失。正式保存仍检查基础版本，避免覆盖第二步的手动修改。

最终未通过要列出具体原因：未解决视觉问题、布局合同、原生文字、PPTX 或浏览器验收哪项失败，不能只显示一个 requires_review。

## 7. 实验与验收

顺序：历史轨迹分析和 Mock → 文件引用改动 → 单轮上下文投影 → 循环调度优化。每批独立开关、独立回退，避免同时修改后无法归因。第一批和第二批可以先并行设计，实验必须逐批对照。

真实调用前提交明确的页面、预计调用数、预算和终止条件，用户确认后执行。沿用简单页 S001 与含公式复杂页 S002 的固定输入，先各一次；若需要额外对照调用，说明新增费用并获得授权。

验收同时查看：

- 固定人工确认问题清单的修复率、新增回归数、漏字与重复字、空格、公式结构和可编辑性。
- 第二步手动修改在第三步的继承情况，Chromium/PPTX/LibreOffice 输出和最终交付通过情况。
- 官方输入/输出/推理/缓存 Token、真实已知费用、未知费用请求、总耗时、总传输量。
- no_change 是否准确找到原因、401/402 是否止损、预算暂停后是否能从最新候选续修。

当前 0/2 是失败基线，不能将“比 0 好”当成质量达标。质量以固定设计稿和问题清单评判。保留旧测试，不修改期望来适应新逻辑。

## 8. 可计算收益与暂时不能承诺的部分

- 流量：上传一次的收益应以本地原始图片的唯一哈希累计大小 + 请求引用开销，与原重复 Base64 载荷比较。当前日志没有逐图片哈希，不能直接给出准确节省百分比；新渲染和新裁图仍需上传。
- Token：优先减少重复字体元数据与整条历史。字节缩小比例不能当成 Token 节省比例；必须通过真实 usage 对照。
- 成本情景计算：若实验实现平均每轮输入降 40%，且有效调用数降 25%，则输入量约为原来的 `0.60 × 0.75 = 45%`，即输入 Token 降 55%。这是计算示例，不是已实现结果；缓存和输出费用仍须单列。
- 不承诺两页固定只需几毛钱。先要求同等或更好修复结果，再比较成功交付的费用，不能以提前停止或跳过视觉复核制造省钱成绩。
- 本次 Visual Agent 已显式关闭 thinking，日志没有大量推理输出证据，先调低思考不能解决主要成本。是否针对复杂失败问题增加一次更充分推理，应按任务总成功率与总成本实验，不能只看单次价格。

## 9. 代码落点与官方依据

- `studio/ai.py::_image_block / _image_region_block`：当前 Base64 图片与三倍放大 PNG。
- `studio/ai.py::visual_agent_turn`：对象投影、历史和视觉输入组织。
- `studio/server.py::run_visual_agent`：诊断/复核调度、no_change、最终验收及候选保存集中在约 1620–2380 行。
- `studio/api_usage.py` 与前端用量入口：上传流量、阶段输入组成、断点/预算状态。
- 独立 Editing Runtime 另行处理完整历史回放，不能把它的机制误当成本次 visual_agent 的实测主因。
